# LessonAI: атомарное сохранение планов всех колледжей

13 октября 2026. Деплой и миграции в production не выполнялись.

## Причина: установленное и ещё неизвестное

Точка общего отказа — `SupabaseService.save_lesson_plan`, вызов `client.rpc('save_lesson_plan_with_daily_limit', parameters).execute()`. Её используют планы META, Q, ETEC, ALT и ATKK через `save_generated_lesson_plan`. Содержание и Word уже подготовлены к моменту обращения к БД.

В предыдущем клиенте исключения почти всех типов заменялись общим сообщением «Не удалось сохранить готовый план…». По нему нельзя отличить отсутствующую функцию, неправильную сигнатуру, права, нарушение CHECK или ошибку SQL. Кроме того, путь был переключён на новую RPC без проверки совместимости до платного AI-запроса.

В старой подготовленной миграции найден дополнительный конкретный SQL-дефект: выходной параметр `RETURNS TABLE (lesson_id uuid, …)` конфликтует с `ON CONFLICT (lesson_id, material_type)` в PL/pgSQL. На отдельной PostgreSQL воспроизведён **42702: ambiguous column reference**. В исправленном теле явно задан `#variable_conflict use_column`. Регрессия проверяет, что без директивы сохранение падает и quota/event откатывается, а с ней проходит.

**Точную серверную причину последнего ручного отказа в подключённой Supabase установить не удалось.** Read-only OpenAPI-запрос с локальными настройками вернул HTTP 401. Это не подтверждает отсутствие RPC или конкретное состояние production-схемы. Исходный PostgreSQL/PostgREST код прошлого отказа не был сохранён старым обработчиком. По сообщению пользователя миграция не применялась; наличие функции и её версии независимо не подтверждено.

## RPC и параметры

Обновлённое сохранение вызывает `public.save_lesson_plan_with_daily_limit` с 13 именованными параметрами:

| Параметр | Тип |
|---|---|
| p_subject, p_topic, p_group_name | text |
| p_course | integer |
| p_duration | text — прежняя конвенция `70 минут`, не изменена |
| p_lesson_date | date — ISO-дата из metadata |
| p_language, p_lesson_type, p_speciality, p_chair | text |
| p_material_content | text — проверенный JSON-объект |
| p_operation_id | uuid — обязательный ключ операции |
| p_existing_lesson_id | uuid / null |

Python проверяет формат UUID до отправки. ФИО, ключи, токены и user_id не передаются в RPC. Пользователь определяется `auth.uid()`, профиль нового занятия — существующей функцией создания. Старый 12-параметровый overload удаляется внутри транзакции миграции без CASCADE, чтобы исключить неоднозначное разрешение RPC. Если есть внешние зависимости, миграция завершится отказом и откатится для ручного разбора.

## Предварительная проверка

Новая `lesson_plan_storage_status()` — STABLE read-only RPC без записи документов/лимита. Проверяет версию контракта 2, точную сигнатуру и имена параметров save RPC, EXECUTE для authenticated, SECURITY DEFINER, существование/контракт функции создания, типы нужных колонок, права владельцев функций, уникальность материалов, ключ таблицы операций, защиту таблицы операций и проектные ограничения колледжей.

`generate_lesson_plan` вызывает `ensure_lesson_plan_storage` **до** content provider. При отсутствующем/недоступном RPC, несовместимой схеме, сетевой или authentication-ошибке генератор не вызывается. Ошибка совместимости отображается безопасным сообщением:

> Требуется обновление базы данных LessonAI. Генерация временно недоступна.

Перед сохранением проводится повторная read-only проверка: схема могла измениться за время AI-генерации. В интерфейсе добавлена кнопка «Проверить доступность сохранения» — она не вызывает AI и не создаёт материалы.

## Атомарность и безопасный повтор

Новая таблица `lesson_plan_operations` хранит ключ `(user_id, operation_id)`, fingerprint запроса и ссылку на занятие. Пользовательские роли не имеют прямого доступа; RLS включён.

RPC получает ту же advisory transaction lock по user_id, что и существующая функция создания. Проверка операции, создание занятия/события квоты, вставка материала и запись операции выполняются в одной транзакции. Любое исключение откатывает всё. Лимит **8** и тарифы не менялись.

Повтор того же ключа и содержания возвращает существующий результат без списания и без повторной перезаписи материала. Изменённое содержание с тем же ключом даёт `IDEMPOTENCY_CONFLICT`. Обновление существующего занятия проверяет владельца и не создаёт событие квоты. Удаление занятия обнуляет ссылку операции; поздний повтор не воссоздаёт удалённый материал.

`PendingLessonPlan` замораживает готовый JSON/metadata и сохраняет один operation_id. На неудаче он остаётся в текущей Streamlit-сессии. Кнопка «Повторить сохранение» использует прежний ключ и не вызывает OpenAI. Есть скачивание готового JSON. При новом входе/выходе черновик очищается, чтобы не переносить материал между аккаунтами. Хранение в сессии не обещает сохранность после перезапуска сервера; для этого нужно скачать JSON.

Для ненормализованного META входа технический meta_attempt_id при подготовке привязан к operation_id: повторная offline-нормализация не меняет fingerprint из-за случайного UUID. `prepare_lesson_plan` позволяет проверять нормализацию и DOCX полностью offline. Старый путь независимого создания урока и upsert материала не используется для планов.

## Диагностика

`services/storage_diagnostics.py` записывает только в local/development/test: RPC, PostgreSQL/PostgREST code, фиксированную краткую причину, этап database_preflight/save и UUID операции. Причины несовместимости схемы проходят allow-list. Исходный текст серверной ошибки, параметры запроса, SQL/DETAIL с данными строк и traceback не логируются. Произвольные идентификаторы также обезличиваются. Полезные поля доступны у обёрнутого исключения в `.diagnostics`.

Общие события создания больше не записывают предмет/тему. Production не включает подробную диагностику по умолчанию; пользователям не показываются сырые SQL-ошибки.

## Что сделать вручную

1. Открыть Supabase SQL Editor нужного проекта. Сначала выполнить `database/checks/lesson_plan_storage.sql`: только метаданные, без чтения материалов/профилей и без записи строк.
2. Сверить таблицы, ограничения колледжей и функции с контрактом. Не переисполнять старые миграции вслепую: 004_atomic зависит от существующих таблиц и create RPC. При несовместимых ограничениях/базовой схеме нужен отдельный разбор, а не автоматическая правка production.
3. После проверки применить **обновлённый целиком** `database/migrations/004_atomic_lesson_plan.sql` вручную. Он включает BEGIN/COMMIT и reload PostgREST schema. Если в БД нет новой RPC, либо стоит предыдущая 12-аргументная версия, эта миграция необходима для нового пути сохранения.
4. В приложении нажать «Проверить доступность сохранения». Это бесплатная read-only проверка; не нужно нажимать «Создать план» для проверки БД.
5. Если готовый материал остался в текущей сессии — «Повторить сохранение», без новой генерации. Отдельные тестовые JSON можно проверить командами выше без OpenAI; SQL-тесты пишут только в одноразовую тестовую БД.

`docs/qa/meta/debug` при поиске отсутствовала, реального проблемного AI-ответа не найдено. Ранее обезличенные структурные снимки сохраняли арифметику/ссылки, но удаляли педагогические тексты: их нельзя выдавать за полноценный восстановленный урок. Уже потерянный старым интерфейсом ответ без полного JSON восстановить этим исправлением нельзя.

Новых платных AI-запросов, автоматического повторного обращения к API, production-миграций и деплоя не выполнялось.
