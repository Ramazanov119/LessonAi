# Подписки AI EDU: настройка и проверка

Реализация остаётся на Python, Streamlit и Supabase. Production не подключался и не изменялся. Миграция 006 устанавливается один раз и оставляет контроль доступа выключенным. Выдача первоначальных подписок и включение контроля — отдельные действия владельца.

## Результаты аудита

- `app.py`: вход по email/паролю Supabase Auth; регистрация с подтверждением email, если оно включено в Supabase. Профиль создаёт Auth-триггер; сервис восстанавливает отсутствующий профиль после входа. Пароли не сохраняются приложением.
- `services/supabase_service.py`: клиент с anon key создаётся заново на каждом rerun. Авторизованный клиент нельзя переносить в `st.cache_resource` или общий singleton: он хранит JWT текущего пользователя. Токены находятся только в серверном `st.session_state`, не в URL или пользовательских metadata. Перезагрузка с потерей Streamlit-сессии требует нового входа. Обновлённые токены теперь сохраняются; выход, новый вход и ошибка восстановления очищают материалы предыдущей сессии.
- RLS существующих таблиц связывает данные с `auth.uid()`. `profiles.role` и старые `subscription_*` остаются для совместимости, но НЕ дают прав и НЕ участвуют в проверке доступа: профиль разрешено менять самому пользователю. `user_metadata` также не является источником прав.
- RPC создания и атомарного сохранения работают как `SECURITY DEFINER`, обходят RLS и потому получают явную проверку подписки в начале, включая повторы идемпотентной операции. Лимит 8 занятий, уникальность темы/даты, длительность 70 минут и контракт сохранения остаются прежними.
- `lessons` и `lesson_materials` получают ограничивающие RLS-политики поверх существующих правил владельца. Триггеры дополнительно проверяют изменения занятий, материалов и событий генерации внутри RPC. Документы в этом репозитории хранятся в `lesson_materials`; Supabase Storage buckets приложение не использует.
- `subscription_admins` закрыта для anon/authenticated. Назначить администратора можно только доверенным SQL владельца. Админ видит перечень Auth-пользователей через проверяемый RPC, но не получает доступ к чужим занятиям.

## Что вручную выполнить владельцу в Supabase Dashboard

1. Сначала подготовить отдельный staging-проект/копию базы и сохранить резервную копию production штатными средствами. В SQL Editor выполнить read-only `database/checks/subscription_preflight.sql`; приватно сохранить определения RPC, ACL, RLS и количества пользователей/занятий/материалов. Проверить неизвестные RPC и политики, особенно если production отличается от репозитория. Произвольные дополнительные SECURITY DEFINER RPC требуют отдельного аудита до включения.
2. Проверить применённые миграции. Для чистого staging порядок: `001_profiles_lessons_quota.sql`, `002_unique_topic_fixed_duration.sql`, `003_lesson_materials.sql`, `004_add_alt_college.sql`, `005_add_atkk_college.sql`, `004_atomic_lesson_plan.sql`, затем `006_subscriptions.sql`. На действующей базе не переисполнять старые миграции вслепую. Сначала подтвердить контракт `004_atomic_lesson_plan.sql` по существующим инструкциям storage. 006 отклоняет старые/неизвестные перегрузки RPC; она не удаляет таблицы, аккаунты, занятия или материалы.
3. После успешной staging-проверки и отдельного разрешения владельца выполнить **только новую 006** на подготовленной production-базе. До изменения production приложение обновлять согласованно: новый код требует RPC `subscription_access` и при его отсутствии блокирует платные функции. Пока `subscription_settings.enforced=false`, существующим пользователям доступ сохраняется даже без подписки.
4. В Authentication → Users проверить личность администратора и скопировать UUID. В `database/checks/subscription_grant_admin.sql` указать UUID и `owner_confirmed := true`, затем выполнить в SQL Editor. Проверить вход администратора и наличие раздела «Админ-панель». Назначение записывается в аудит; SQL Editor может дать `actor_id = NULL`, это доверенное действие владельца. Старые роли/metadata не переносить автоматически.
5. Согласовать срок первоначального доступа, перечень действующих клиентов и точный момент отсечения регистраций. Посмотреть `SELECT id,email,created_at FROM auth.users ORDER BY created_at;`. В **отдельном** `subscription_initial_grants.sql` указать `cohort_cutoff`, `initial_end` с timezone и `owner_confirmed := true`. Сценарий добавит только отсутствующие подписки и запишет аудит; существующие не перезапишет. Он намеренно не выполняется вместе с миграцией. Различающиеся договорённости можно выдать через админ-панель индивидуально.
6. Проверить строки `admin_subscription_users()` из приложения, даты, приостановки, сохранность документов; сравнить исходные количества. Самому администратору тоже нужна подписка для платных функций; управление подписками доступно ему независимо от её срока.
7. Перед включением провести проверки из раздела ниже. В `subscription_activate.sql` установить подтверждение владельца и выполнить. Сценарий потребует хотя бы одного администратора и действующий неприостановленный доступ **у всех текущих Auth-пользователей**, чтобы никого не отключить случайно. При ошибке сначала разобрать пользователей без доступа и выдать согласованные подписки. После включения новый пользователь без подписки получает страницу оплаты.

При аварии владелец может временно выполнить `UPDATE public.subscription_settings SET enforced=false WHERE id;`: это записывается в аудит и возвращает доступ всем авторизованным пользователям, включая приостановленных. Это бизнес-решение владельца; для обычного восстановления связи отключать контроль не нужно. Не откатывать удалением таблиц или документов.

## Streamlit Community Cloud

Использовать существующее приложение и `app.py` как entrypoint, текущий `requirements.txt`; новых зависимостей нет. Новая публикация/`git push` выполняется только после отдельного разрешения владельца. Секреты хранятся в **Settings → Secrets**, затем Save; локально — в игнорируемом `.streamlit/secrets.toml`. См. [официальную инструкцию Settings](https://docs.streamlit.io/deploy/streamlit-community-cloud/manage-your-app/app-settings) и [Secrets](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/secrets-management).

Сохранить существующие ключи AI и настройки презентаций. Добавить или проверить:

```toml
SUPABASE_URL = "https://YOUR_PROJECT.supabase.co"
SUPABASE_ANON_KEY = "YOUR_ANON_OR_PUBLISHABLE_KEY"
SUBSCRIPTION_PAYMENT_INSTRUCTIONS = "Для оплаты обратитесь к ... Укажите email аккаунта. Доступ открывается после подтверждения администратором."
```

Вместо многоточия владелец указывает реальный контакт и согласованные инструкции. Service role / secret key и пароль базы приложению не нужны: все операции выполняются с JWT пользователя, права проверяются в SQL. Не размещать их в Cloud secrets этого приложения. Настройки Supabase Auth email confirmation, redirect URLs и существующие аккаунты менять не требуется. Отдельного клиентского флага включения подписок нет: единственный переключатель в защищённой таблице базы.

## Поведение панели и ограничений

Поиск по ФИО/email, фильтры колледжа/статуса; показатели по всем пользователям, «активных» включает истекающих за 7 дней. Таблица и CSV содержат дату окончания и оставшиеся дни. CSV выгружает текущий фильтр, кодировка UTF-8 BOM для Excel, пользовательские формулы экранируются. Даты таблицы имеют timezone; выбранная в форме дата — последний оплаченный день Алматы, доступ заканчивается в 00:00 следующего дня.

Продление: от большего из текущего момента и существующего окончания на 7/30/90/365 дней. Установка даты допускает сокращение/истечение срока, требует подтверждения. Приостановка требует причины и подтверждения; собственную приостановку запрещают UI и SQL. Продление сохраняет флаг приостановки: снять его нужно действием «Возобновить». Возобновление само по себе не продлевает истёкшую подписку. Изменение тарифа и причины фиксируется в истории вместе с предыдущими и новыми значениями.

Оплата записывается только администратором после подтверждения получения: сумма в тенге, дата, способ, комментарий, проверивший администратор и время проверки. Запись оплаты **не продлевает автоматически** подписку. Она видна в истории с действием `payment`; исправление ошибочной оплаты требует отдельной согласованной процедуры владельца (редактирование/удаление из клиентского API запрещено).

Доступ при включённом контроле: есть подписка, `starts_at <= now() < ends_at`, `suspended=false`. Никакого обхода для администратора при генерации нет. При ошибке статуса UI блокирует платные функции; прямые запросы ограничивает база. Предупреждения показываются при каждом посещении в интервалах 7–4, 3–2 и 1 день, используя время Supabase и округление оставшихся суток вверх. Email и платёжных шлюзов нет. Уже скачанный файл отозвать невозможно; серверные данные не удаляются.

## Проверки

Python/Streamlit (без подключения к Supabase и AI):

```sh
PYTHONPYCACHEPREFIX=/tmp/lessonai-pycache .venv/bin/python -m unittest discover -s tests -p 'test_*.py'
```

Изолированный PostgreSQL 17 через Docker, без открытых портов/production credentials; контейнер автоматически удаляется:

```sh
python3 tests/run_subscription_sql.py
```

`tests/sql/subscription_setup.sql` — минимальная имитация схемы Auth **только для disposable PostgreSQL**, никогда не запускать в Supabase. SQL-проверки проверяют реальные GRANT/RLS/SECURITY DEFINER, отсутствие самоназначения прав, разделение пользователей, приостановку и истечение, восстановление, атомарное создание занятия/материала, повтор RPC после блокировки, аудит и сохранность аккаунтов/документов/квоты. Python/Streamlit-тесты проверяют fail-closed при ошибках/некорректных ответах, отдельные клиенты, новые токены, UI-права, страницу ограничения и безопасный CSV. Остальные существующие тесты проверяют генераторы документов и прежнее сохранение.

Перед production повторить на staging Supabase через **anon key + JWT** двух разных пользователей (не service role): прямые чтение/запись чужой подписки, попытка вызвать admin RPC обычным пользователем, чтение/запись материалов с истёкшей подпиской, одновременные браузерные сессии, сохранение каждого типа материала и загрузку старых документов. Docker не моделирует PostgREST, настройки проекта и реальные внешние AI-провайдеры; эти проверки нужны владельцу отдельно. До их подтверждения контроль на production не включать.
